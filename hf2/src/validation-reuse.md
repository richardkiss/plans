# Reuse the HF2 generator tree during block validation

## Problem

A full node needs the committed root before running puzzles. It also needs puzzle hashes, spend conditions and sometimes a shorter wire encoding. Today the commitment checker hands Python a digest and drops the parsed tree. The runner receives bytes again. The proposed unit of reuse is one candidate generator in one validation job. HF2 activation is the sole entry gate.

## Evidence

Source inventory from chia-blockchain worktrees `hf2-cap-prehash` (e84343d37) and `generator-reencode` (931642b74), and chia_rs `reencode-c-0.52.2-combined` (f3c81678). These are different snapshots. Counts below are static call-path counts for successful paths with a generator. They are hypotheses for counters, not benchmark measurements.

| Route | Checked reads and hashes today |
|---|---|
| Fresh finished block or sync, no supplied conditions | In `multiprocess_validation._pre_validate_block`, one decode and whole-root hash, then a second decode and interning in `run_block_generator2`. Body check 7a in `validate_block_body` decodes and hashes again. Total three reads and two whole-root hashes. Puzzle hashes use a separate cache in the runner. |
| Fresh unfinished block | `add_unfinished_block` checks the header under the mutex, runs the generator outside the mutex, then calls `validate_unfinished_block`, which checks the header again and calls body validation. Three commitment reads/hashes plus the runner's read. Do not move puzzle execution under the mutex. |
| Finished block with matching unfinished result | An incoming buffer, when present, gets its own root check before replacement with the cached buffer. The supplied-conditions worker path skips execution and its early commitment check. Body validation checks the selected buffer. Missing incoming bytes remove the first check. Matching foliage alone does not authenticate supplied bytes. |
| Optional downstream recompression | The separate Python branch calls `smaller_generator` after unfinished validation, before caching/relay. Fresh finished and sync paths invoke it after prevalidation and before `blockchain.add_block` and its body check. The matched unfinished path disables the redundant finished recompression. Each attempted re-encode reads the bytes again and builds serializer state. A shorter replacement before body validation changes which bytes body check 7a sees. |
| Farming or root-only callers | Block creation needs a commitment without execution. Preserve that entry point and count it separately. |

`wheel/src/api.rs::tree_hash_2026` builds a temporary allocator and DAG-aware hash cache. `crates/chia-consensus/src/run_block_generator.rs::run_block_generator2` decodes, interns into a second allocator, calculates interned vbytes, visits puzzle roots and hashes them during spend processing. Interning and tree hashing serve different purposes. One deserialize can still involve two allocators and several traversals. The level-0 encoder also builds its own serializer state. Removing its byte read alone does not remove that work.

## Target

Select the new route using `get_flags_for_height_and_constants(pre_sp_tx_block_height(...), constants) & INTERNED_SPEND_LIST` after existing version checks. Compute this for each candidate's ancestry and signage point. A below-fork candidate during historical sync or after a reorg takes the existing byte commitment, runner, reference and canonicality paths. The wire prefix, block height alone and local peak are insufficient selectors.

Keep one private Rust owner per candidate containing the interned allocator, root, vbytes, and an allocator-local tree hash cache. Initially use the existing bounded decoder and interner. Drop the decode allocator after transfer. Compute the commitment over the interned root and establish equality with the old digest in parity tests. An optional subsequent optimization may decode directly into the final representation if measurements justify it. Keep the generator immutable while execution appends allocator nodes. Discard cache entries before any allocator rollback/index reuse. Never send node pointers or an allocator through Python worker serialization.

A candidate Rust interface is a checked HF2 runner accepting immutable bytes, expected root, refs, execution budget, flags, signature inputs and network constants. It compares the root before executing any puzzle. The Python wrapper must preserve the existing order of the generator-root and foliage checks, including multi-error inputs. A private prepare/check operation followed by consume/run within the same worker can preserve intervening checks; a single call requires reproducing their ordering explicitly. Preserve standalone root-only checks. Return owned conditions and a commitment result linked to the *exact* candidate, validation context and verified expected root. Conditions alone do not establish provenance.

Use the commitment cache for puzzle hashing within the same allocator. The current cache retains selected repeated pairs and long atoms. Measure cache hits and SHA work; sharing a cache alone does not ensure a singly referenced puzzle root survives the whole-root traversal. Register requested puzzle roots for retention, or collect their hashes as the commitment traversal completes. Discovering them must preserve malformed-spend error ordering and early root rejection. Prefer explicit retention of the required roots to caching every intermediate hash. Preserve the DAG-aware traversal in the root-only path.

## Pathway

1. **First independently reviewable PR:** factor only the active-HF2 preparation in Rust into a private constructor used by the existing runner. Keep all legacy dispatch, public binding signatures, cost/error behavior and Python calls. Add differential fixtures for the preparation output and a benchmark fixture recording bounded decode count, intern count, whole-root and puzzle hashes, and peak allocation. This is a reviewable ownership seam. The first end-to-end reduction arrives in step 2.
2. Wire the checked execution route into fresh finished-block prevalidation. Root verification and execution share one decode. Preserve the body fallback. Introduce exact-candidate evidence only after documenting each caller and its ownership boundary. Prefer a private orchestration object coupling immutable input with the worker result. Across worker boundaries use request/result association with the submitted block held by the coordinator; a later replacement needs new evidence or a fresh check. Never trust serialized peer data or a Boolean supplied alongside arbitrary conditions.
3. Carry evidence through the finished body and unfinished paths. Preserve checks under the lock that protect mutable chain state. Move only immutable-input preparation out of critical sections and recheck chain-context identity when reacquiring the lock. A different incoming representation gets a bounded root check even when the unfinished result matches. Release trees at job end. Across the unfinished/finished cache boundary retain compact evidence and owned results, with existing eviction policy.
4. Optionally encode from the same live allocator after successful validation or carry a smaller candidate generated by the worker, then apply it only at existing success points. Return owned replacement bytes only when strictly shorter. Preserve the original on ties or encoding failure. Authenticate the replacement via trusted same-tree serialization provenance, with a body fallback until parity is established. Measure extra time on the validation critical path, discarded candidates and peak memory before enabling. Keep compression level a local policy. Introduce an encoder entry point taking an already-interned representation only if profiling supports that additional change.

## Decisions and acceptance

- The early wire-size check uses `max_canonical_blob_size(MAX_BLOCK_COST_CLVM, COST_PER_BYTE)` before decode/hash. The inspected runner separately uses its actual execution budget for a decoder bound. Preserve both checks at their existing semantic points and preserve corresponding errors. A small declared cost must not silently change a commitment failure into an execution failure, or vice versa. Continue charging interned vbytes times cost per byte plus the existing execution and condition costs. Wire length and compression level never determine charged vbytes.
- Validate wrong root before puzzle execution; preserve transaction-info/foliage commitments, generator absence and zero-root rules, reference checks, signature-validation flags, returned conditions, error codes and ordering. A substitute buffer must pass its own cap and checked decode even when another encoding of the same committed tree was valid.
- Differentially run old/new paths on normal block fixtures, alternate accepted encodings, wrong commitments, malformed input, oversized inputs, low declared cost, missing generator, supplied conditions and differing signature modes. Include mixed-era sync and a reorg crossing activation in both directions, exact pre-SP height immediately below and at HF2, and cases where candidate and pre-SP heights straddle activation. Assert the old path's call counters below HF2.
- Count operations by route using identical input and hardware. Measure worker and end-to-end p50/p95 latency, peak RSS at realistic worker concurrency, and mutex time. Target one bounded decode and one whole-root hash per fresh active-HF2 candidate across the normal verification/execution/body route. Count distinct incoming encodings and fallback paths separately. Check virtual cost, acceptance and conditions independently of timing. Roll out one route at a time with the old orchestration available until parity and resource measurements hold.

## Status

As of 2026-11-24, generator reuse remains a design proposal. Performance measurements are pending.

The draft chia-blockchain PR uses a released chia_rs dependency and applies a temporary Python size bound before hashing at commit `578fb4b5a`. The chia_rs size-bound PR is backlogged. The proposed reuse path must preserve the early bound.
